# План проекта «Авито.Кухня»

Этот документ фиксирует понимание тестового задания, границы MVP,
основные бизнес-сценарии и принятые технические решения.

Документ будет дополняться по мере проектирования и реализации сервиса.

## 1. Задача

Необходимо разработать MVP backend-сервиса «Авито.Кухня» — платформы,
через которую пользователи могут просматривать заведения, изучать меню
и оформлять заказы 

Заведения должны иметь возможность передавать информацию о меню,
получать заказы и изменять их статусы.

Клиентскую web-часть разрабатывать не требуется. Взаимодействие с ней
представлено в виде REST API.

## 2. Участники системы

### Пользователь

Пользователь может:

- посмотреть список заведений;
- открыть меню выбранного заведения;
- найти блюдо по названию — как внутри меню, так и по всей площадке;
- увидеть доступные блюда;
- оформить заказ;
- получить информацию о заказе;
- отслеживать статус заказа;
- отменить заказ, пока заведение его не приняло.

Аутентификация и авторизация пользователей в рамках MVP не реализуются.

### Заведение

Заведение может:

- передать или обновить своё меню;
- изменить доступность блюда;
- получить новые заказы;
- принять или отклонить заказ;
- изменить статус принятого заказа вплоть до выдачи.

Для демонстрации интеграции будет реализован отдельный сервис
тестового заведения.

### Основной сервис

Основной сервис «Авито.Кухня»:

- хранит сведения о заведениях и меню;
- принимает пользовательские заказы;
- проверяет корректность заказа;
- рассчитывает и сохраняет итоговую стоимость;
- предоставляет заказы соответствующему заведению;
- хранит актуальные статусы заказов.

## 3. Основные пользовательские сценарии

### Сценарий 1. Поиск блюда

1. Пользователь ищет блюдо по названию.
2. Сервис возвращает подходящие доступные позиции активных заведений.
3. Вместе с каждой позицией возвращается заведение, где её можно заказать.

Поиск не зависит от того, знает ли пользователь конкретное заведение:
он идёт от блюда, а не от заведения.

### Сценарий 2. Просмотр заведений и меню

1. Пользователь запрашивает список доступных заведений.
2. Выбирает одно заведение.
3. Запрашивает его меню, при необходимости фильтруя по названию блюда.
4. Сервис возвращает список блюд с ценами и информацией о доступности.

### Сценарий 3. Создание заказа

1. Пользователь выбирает блюда одного заведения.
2. Указывает количество каждого блюда.
3. Отправляет запрос на создание заказа.
4. Сервис проверяет заведение, блюда и их доступность.
5. Сервис рассчитывает итоговую стоимость.
6. Заказ сохраняется со статусом `created`.
7. Пользователь получает идентификатор и данные созданного заказа.

Если хотя бы одно блюдо недоступно или не принадлежит выбранному
заведению, заказ не создаётся.

### Сценарий 4. Просмотр заказа

1. Пользователь передаёт идентификатор заказа.
2. Сервис возвращает состав, стоимость и текущий статус заказа.

### Сценарий 5. Отмена заказа

1. Пользователь передумал и отменяет заказ.
2. Сервис проверяет, что заказ принадлежит этому пользователю.
3. Отмена разрешается, только если заведение ещё не приняло заказ.
4. Заказ переходит в статус `cancelled`.

Если заведение уже приняло заказ, отмена отклоняется: продукты могли
пойти в работу, и такой случай требует согласования с заведением.

## 4. Сценарии заведения

### Сценарий 1. Управление меню

1. Заведение передаёт меню основному сервису.
2. Основной сервис сохраняет новые блюда и обновляет существующие.
3. Заведение может отдельно изменить доступность конкретного блюда.

### Сценарий 2. Обработка заказа

1. Заведение запрашивает новые заказы.
2. Получает заказы со статусом `created`.
3. Принимает или отклоняет заказ.
4. Для принятого заказа обновляет статус по мере приготовления.

Последовательность статусов:

`created → accepted → preparing → ready → delivered`

Из статуса `created` заказ также может перейти в `rejected` — если
заведение отказалось, и в `cancelled` — если пользователь передумал.

Терминальные состояния: `rejected`, `cancelled`, `delivered`.

## 5. Основные бизнес-правила

- Один заказ может содержать блюда только одного заведения.
- Количество каждой позиции должно быть больше нуля.
- В заказ можно добавить только существующее и доступное блюдо.
- Цена блюда сохраняется в позиции заказа на момент его создания.
- Последующее изменение цены в меню не изменяет стоимость созданного заказа.
- Итоговая стоимость заказа рассчитывается на стороне основного сервиса.
- Статусы заказа могут изменяться только в разрешённой последовательности.
- Отменить заказ может только его владелец и только до принятия заведением.
- Поиск возвращает блюда, которые действительно можно заказать: только
  доступные позиции активных заведений.
- Повторный запрос на создание заказа не должен создавать дубликаты.
- Партнёрское API заведений должно быть закрыто от обычных пользователей.

## 6. Входит в MVP

- основной сервис на Go;
- демонстрационный сервис заведения;
- REST API для пользователей, включая поиск блюд;
- REST API для заведений;
- PostgreSQL;
- миграции базы данных;
- OpenAPI-спецификация;
- запуск через Docker Compose;
- линтер и статический анализ;
- автоматические тесты основных сценариев;
- CJM пользователя и заведения;
- C4-диаграмма;
- схема базы данных;
- README с инструкцией по запуску.

## 7. Не входит в MVP

- frontend;
- регистрация и авторизация пользователей;
- настоящая оплата;
- управление курьерами;
- расчёт маршрута и стоимости доставки;
- уведомления;
- отзывы и оценки;
- рекомендации;
- поиск по геолокации;
- фильтры по кухне, категории и цене;
- отмена заказа после того, как заведение его приняло;
- заказ из нескольких заведений;
- полноценная административная панель.

## 8. Предварительная интеграция с заведением

Меню хранится в основном сервисе «Авито.Кухня».

Демонстрационный сервис заведения:

1. Передаёт и обновляет своё меню через партнёрское API.
2. Периодически запрашивает новые заказы.
3. Принимает или отклоняет полученные заказы.
4. Обновляет статусы принятых заказов.
